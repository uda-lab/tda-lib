# Mathematical Issue decomposition

Use only when the governing Issue or dot requests decomposition. Roadmap intake, Issue
granularity and authorization belong to dot; do not impose a fixed milestone sequence,
line-count limit, charter or new template. Preserve existing Issue templates.

Read the Issue and decisions, authoritative sources and available mathlib/TauCeti APIs.
Identify actual mathematical dependencies, unresolved conventions and proof risks. Record
needed decisions and child work on GitHub, not in a second local roadmap. Dependencies
normally refer to declarations on develop. A missing API may warrant reconnaissance before
implementation; dot chooses the work boundaries and authorizes `agent:ready`.

Where an Issue requires a statement contract, specify its domains, hypotheses, quantifier
order, conventions and interface guarantee. Distinguish a frozen public name/type from a
requirement merely to prove the source result. Source ↔ Lean review is independent from the
implementer and records its actual comparison mode. Unavailable sources remain explicitly
outstanding under the loop’s source-fidelity policy.

Public theorem holes cannot pass the live axiom audit. Issue-authorized private staging
contracts may use the existing `ALLOW_SORRY` mechanism on develop only; they must not enter
pinned theorem closures or stable releases. A Prop definition can express a statement when
that interface is the intended deliverable. Neither device counts as a discharged proof.
Statement changes need renewed independent fidelity review; never silently weaken a claim.

A dispatch carries source anchors, declaration/API dependencies, scoped acceptance conditions,
known traps and applicable decisions. Size jobs to available resources and maintain explicit
ownership; no fixed vendor or plugin is assumed. When new dependencies or mathematical
changes emerge, record them on the Issue and let dot revise scope or split work. Preserve
already validated results and report what remains unproved.
