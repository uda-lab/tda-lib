# Claude Code cloud setup

`scripts/claude-cloud-setup.sh` is a standalone Bash script for the Setup Script field in an Anthropic-hosted Claude Code environment. Paste the file contents into that field. It does not require a checked-out repository or GitHub credentials: it creates an isolated project from the checked-in Lean and Lake pins, installs the pinned Elan/Lean toolchain when possible, and runs only `lake exe cache get`. It never runs `lake update` or a library build.

Instead of pasting, the Setup Script field can run the script from the fresh clone, so that the pins follow the checked-out branch and the field need not be updated when they change. The environment's setup script starts in the directory that holds the repository checkouts:

```sh
#!/usr/bin/env bash
set -u
if [ -f tda-lib/scripts/claude-cloud-setup.sh ]; then
  bash tda-lib/scripts/claude-cloud-setup.sh || echo "tda-lib setup incomplete; see STATUS.txt"
else
  echo "tda-lib checkout not found; Lean setup skipped"
fi
```

The result is recorded in the same `STATUS.txt`. The pasted form remains the one to use when the environment may start without this repository checked out.

The script stores the prepared project, logs, status, checksum manifest, and next-step instructions under `/root/.cache/tda-lib-claude-setup`; mathlib `.ltar` artifacts go to `/root/.cache/mathlib` so the repository's normal `scripts/bootstrap.sh` can reuse them. Its status is `warm` only when Elan, Lean 4.35.0, all manifest-pinned and clean package sources, and a complete mathlib cache with per-archive checksums are verified. A timeout, missing cache artifact, network failure, or Elan version mismatch is recorded as partial; partial state is never reported as a warm cache. A checkout pin mismatch is instead reported by `scripts/claude-cloud-activate.sh` with exit 2; that helper leaves `STATUS.txt` unchanged. Each download/install/cache stage has a time limit and an elapsed-time record, with a 250-second overall work budget to leave time for status writing. This budget is an implementation target, not a measurement of Anthropic-hosted runtime.

The stage before it copies the three companion skills `github-driven-workflow`, `github-loop-engineering` and `lean-formalization-discipline` from <https://github.com/t-uda/skills> into `$HOME/.claude/skills/<skill>`, so that `scripts/preflight.sh` finds them without an install step in the session. The script fetches the source at the pinned commit `f3bc1c250d2a47871c6527db2d7be779d72bef79` (a `readonly` in the script; it is not a branch), checks that the checked-out `HEAD` equals the pin, and only then runs the source's own `scripts/install-skill.sh <skill> claude "$HOME" --copy`. Copy mode is required because the default relative symlinks would dangle once the temporary clone is removed. Nothing downloaded is piped to a shell. The stage has its own 40-second limit inside the 250-second work budget, runs after the cache stages so that it never takes time from them, and records `skills_seconds`. An existing skill directory is never replaced: an identical copy from an earlier run is recorded as `present`, a different one as `conflict` and left untouched, so a re-run changes nothing. `STATUS.txt` records `skills_status` (`ready`, `conflict`, `incomplete`, `blocked`; `not-attempted` remains if setup stops earlier), `skills_detail`, `skills_repo`, `skills_commit_requested`, `skills_commit_found`, `skills_dir` and one `skill_<name>` line per skill (`installed`, `present`, `conflict`, `failed`, `missing-in-source` or `not-attempted`). Like `sandbox_status`, this is independent of `state`: a skills failure never turns a `warm` snapshot into `partial`, and installed skills never make a `partial` one `warm`. When `skills_status` is not `ready` or a session reports a skill `MISSING`, install it from the recorded commit as described in [Prerequisites](orchestration.md#prerequisites). Raising the pin is an infrastructure change to the script and this document.

The last stage puts `bwrap`, the bubblewrap sandbox executable, on `PATH` when it can, because the full gate `scripts/check.sh` ends with the Comparator step and `scripts/check-comparator.sh` refuses to run without `bwrap`. If `bwrap` is not installed and `apt-get` is, the script runs `apt-get update` and `apt-get install -y --no-install-recommends bubblewrap` within the same work budget. `STATUS.txt` records the result as `sandbox_status` (`ready`, `incomplete`, `unavailable` or `blocked`; the initial value `not-attempted` remains if the setup is stopped before this stage runs) with `sandbox_seconds` and `sandbox_detail`. `ready` means that `bwrap` is on `PATH`; it does not mean that the Comparator's own sandbox start-up probe passes in the session. It is reported separately from `state`: a snapshot is `warm` or `partial` by the cache stages alone. When `sandbox_status` is not `ready` and `bwrap` is not on `PATH`, install the `bubblewrap` package before a full `scripts/check.sh`; do not skip or bypass the Comparator step.

In each fresh repository checkout, ask Claude to read `/root/.cache/tda-lib-claude-setup/STATUS.txt` and `INSTRUCTIONS.txt`, then run the activation helper. If it reports a pin or existing-path conflict (exit 2 or 4), stop and report it. If it exits 3, inspect the status: run `scripts/bootstrap.sh` only when the current pins match and Lean 4.35.0 is ready; otherwise stop and report. On exit 0, run `scripts/bootstrap.sh` to materialize and revalidate the cache:

```sh
bash scripts/claude-cloud-activate.sh
bash scripts/bootstrap.sh
```

The activation helper compares `lean-toolchain`, `lakefile.toml`, and `lake-manifest.json` byte-for-byte before linking cached dependency sources. It also checks every package revision, tracked and untracked source cleanliness, and the saved `.ltar` checksums. It leaves an existing `.lake/packages` path untouched. `scripts/bootstrap.sh` uses the repository's guarded Lean wrapper and mathlib's hash-checked cache to materialize oleans at this checkout's path. If the helper reports a pin/path mismatch, or bootstrap fails, stop before a full build and report the status and relevant log. Do not attempt a cold mathlib source build as a fallback.

A hosted session has no review broker (`REVIEW_ACQUIRE_SCRIPT` is unset) and, unless the snapshot's `skills_status` is `ready` (the setup script copies the companion skills, above), no installed companion skills. Request the PR review there by the comment route of [lean-review-routing](../.agents/skills/lean-review-routing/SKILL.md#pr-review-evidence-for-github-driven-workflow-8): post `@codex please review this PR` on the PR with the session's GitHub tool.

Suggested first prompt:

> Read `/root/.cache/tda-lib-claude-setup/STATUS.txt` and `INSTRUCTIONS.txt`, then run `bash scripts/claude-cloud-activate.sh`. If it exits 2 or 4, stop and report. If it exits 3, run `bash scripts/bootstrap.sh` only if Lean 4.35.0 is ready and the repository pins match. On exit 0, run `bash scripts/bootstrap.sh`. Stop before any full build if bootstrap fails.

The current setup project pins `leanprover/lean4:v4.35.0`, mathlib tag `v4.35.0` resolved to commit `56a005855ea17e0b0958f73ec801ae140b0a1679`, and all transitive revisions from the current `lake-manifest.json`. Keep the embedded files in `scripts/claude-cloud-setup.sh` synchronized with the repository pins, including the package `version`. `bash scripts/test-guards.sh` checks that each embedded copy is byte-for-byte equal to the tracked file and names any file that has drifted; it runs on macOS and Linux and in the CI `check` job. `scripts/test-claude-cloud-setup.py` repeats that check and also exercises the setup and activation scripts against mocked tools, including a mocked `apt-get` for the sandbox stage and an offline fixture repository for the skills stage (pin match, pin mismatch, unreachable source, conflict and idempotent re-run); it runs only by hand on Linux and is not part of `scripts/check.sh` or CI.

The prepared packages under `/root/.cache/tda-lib-claude-setup/project/.lake/packages` are shared by every session that uses the snapshot, and a plain `git status` in one of them refreshes its index. Readers should run `GIT_OPTIONAL_LOCKS=0 git -C <package> status` (or any other read-only `git` command) instead. This is guidance only: the scripts do not set it, and `INSTRUCTIONS.txt` repeats it.

Anthropic's [current cloud-environment documentation](https://code.claude.com/docs/en/cloud-environments#environment-caching) says setup scripts run as root on Ubuntu 24.04 before Claude launches, while the repository is available as a fresh clone to the session. It does not document the clone path or guarantee the checkout is available to the setup script, so this script does not depend on either. Setup-time environment variables are not available. A filesystem snapshot is reused only when setup finishes in roughly five minutes; it expires after roughly seven days and is rebuilt when the script or allowed hosts change. SessionStart hooks run on every session start and resume, so the cache materialization step remains an explicit agent action instead of a heavy hook. A download that itself exceeds the setup window cannot be made reusable by splitting extraction into a session step.

The setup uses GitHub release assets and Mathlib's Azure cache endpoint `lakecache.blob.core.windows.net`. Trusted network access must permit those hosts and package-source downloads. This work does not change environment network rules, Claude account settings, secrets, or permissions. Do not add secrets to the setup script.
